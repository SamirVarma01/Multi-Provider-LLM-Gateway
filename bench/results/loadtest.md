# Gateway overhead

Generated by `scripts/loadtest` on 2026-11-09T13:31:35Z at commit `5b8bab0`. Host: Apple M2, Darwin; Docker VM: 8 CPUs, 3.8 GiB memory. The load generator saw 8 CPUs.

Each level sends the same load twice: straight to the mock provider, and through the gateway to that same mock. The mock's latency is fixed: first token after 50ms, then 32 tokens at 100 tokens/s. The direct run is the baseline, and the difference is what the gateway adds: authentication, the Redis rate limit, the Postgres reservation, routing, the extra network hop, and decoding and re-encoding every chunk. Settling the charge runs after the response, so it adds load but not latency.

- **Overhead** is the gateway's percentile minus the direct run's percentile, not a percentile of per-request differences. At p99 it is noisy, and it can come out negative.
- **Latency** runs from when the schedule meant to send a request to the end of its response, so a generator that falls behind shows up as latency instead of hiding it.
- **Fixed rate** sends a request every 1/rate seconds whatever the earlier ones are doing. **Fixed concurrency** keeps that many requests in flight, each worker sending its next request when the last one ends.
- Each level runs 3s unmeasured, then 20s measured. Benchmark keys have rate limits and a budget far above the load, so every request takes the full rate-limit and budget path.
- The generator, gateway, mock, Postgres and Redis share one Docker VM on one laptop, so these numbers compare the two paths. They are not a server's capacity.

## The gateway's own overhead metric

`gateway_overhead_seconds` is each request's total time minus the time spent waiting on the provider, measured inside the gateway (design D23). The client's figure is the difference in mean full-response latency, so it also includes the extra network hop, and any time the generator's own scheduling added to one run and not the other.
